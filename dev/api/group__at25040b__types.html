enum class at25040b::BlockProtect : uint8_t
strong

Block write protection level, BP1:BP0 in the status register (Table 6-4).

The protected part is always at the top of the array; the addresses depend on the variant (ProtectedFrom()).

Enumerator
None 

BP1:BP0 = 00: nothing protected. The value of a new part.

UpperQuarter 

01: the top quarter is read-only (0x180 to 0x1FF on the AT25040B).

UpperHalf 

10: the top half is read-only (0x100 to 0x1FF on the AT25040B).

All 

11: the whole array is read-only.

◆ Error

enum class at25040b::Error : uint8_t
strong

Why a call failed. Every call of the driver returns one of these in its Result.

Values 0 to 9 are the shared base set; chip-specific values start at 16. [[nodiscard]] on the type: a function that returns a bare Error cannot have it ignored either (KB-CPP20-037).

Enumerator
Ok 

The call succeeded.

NotInitialized 

EnsureInitialized() has not succeeded, or Deinitialize() ran since.

InvalidArgument 

An argument or a Config field is out of range; nothing was sent.

Bus 

A transfer hook (Transfer(), EnsureInitialized()) returned false.

Timeout 

After the start, the status read busy (0xFF) for longer than Config::write_timeout_us: a write cycle that does not end, or the chip was unplugged since and MISO floats high.

DeviceIdMismatch 

At start-up, the bus answers but not like an AT25xxxB: the status is neither idle nor busy (0x05 is MOSI echoed onto MISO), or the write enable latch did not follow WREN and WRDI (MISO stuck low, no chip, or WP held low with Config::check_write_enable on).

Crc 

Not returned by this driver (the chip sends no CRC).

Busy 

Not returned by this driver: every call waits for a write cycle.

DeviceFault 

Not returned by this driver (the chip reports no faults).

Unsupported 

Not returned by this driver.

NoDevice 

At start-up, the status read 0xFF for longer than Config::write_timeout_us: nothing drives MISO (pulled or floating high), so no chip answers.

BusNoise 

A reply no working chip gives: two reads of the same thing differed, or after the start a status byte was neither idle nor busy.

WriteProtected 

WREN did not set the write enable latch: the WP pin is low (tied low, or the port's WP hook did not release it), or the WREN frame was lost. Nothing was written.

BlockProtected 

The range lies in the block-protected part of the array (BP1, BP0); only the status was read, nothing was written.

WriteMismatch 

After a write the chip does not hold what was sent: the read-back differed (Verify::ReadBack), the write enable latch was still set after the write (the chip ignored it), or BP1 and BP0 did not take.

Pin 

The port's GpioSet() could not drive WP (release or park); the name and meaning the handbook gives a failed pin hook (KB-CPP-047).

◆ Variant

enum class at25040b::Variant : uint8_t
strong

Which part of the family is fitted. The chip cannot tell its size, so it is configured.

The three parts share the instruction set, the 8-byte page and the status register; only the array size differs, and only the AT25040B uses address bit A8 (datasheet "Description", Table 6-1 note 1).

Enumerator
At25010b 

128 bytes (1 Kbit).

At25020b 

256 bytes (2 Kbit).

At25040b 

512 bytes (4 Kbit), A8 in the opcode. The default.

◆ Verify

enum class at25040b::Verify : uint8_t
strong

Extra verification for one Read() or Write() call, chosen per call.

The datasheet needs neither: Verify::None, the default, sends only what it needs, plus the status reads that keep a call off a busy chip. Verify::ReadBack costs transfers on the bus and is for a caller that has no CRC or signature of its own over the data.

Enumerator
None 

Each chunk read once; no page read back. The default.

ReadBack 

Read(): each chunk read twice and compared (BusNoise), twice the READs. Write(): each page read back and compared (WriteMismatch), one READ more per page.

◆ kReadChunkBytes

constexpr std::size_t at25040b::kReadChunkBytes = 16
inlineconstexpr

Data bytes per READ transfer: Read() splits longer requests into transfers of at most this many data bytes.

The datasheet sets no limit (a READ continues through the array, section 6, "Read Sequence"), so this is a design choice, sized by what it costs:

  • The port: kMaxTransferBytes (18) is the longest transfer a port must take, and the driver object holds two buffers of that size (36 bytes, see detail::EepromBus). A whole-array chunk would make that 2 x 514 bytes in every driver object and every port's DMA descriptor.
  • The bus: CS goes high after each chunk, so a long Read() never holds a shared bus for more than 18 x 8 = 144 SCK cycles: 29 us at the 5 MHz of the full supply range, 7.2 us at 20 MHz.
  • The overhead: 2 command bytes per 16 data bytes (11 %); halving the chunk to 8 would cost 20 %, doubling it to 32 saves 5 % of the bus time and doubles the buffers.
  • Verify::ReadBack: two whole pages per chunk, so the compare buffer is 16 bytes.

Not a Config value: the buffers are sized at compile time from it, and no setting of it changes what the chip does. A port with a smaller transfer limit cannot use this driver as it is.
